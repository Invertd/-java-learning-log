# 八股卡片

> **怎么用**：每天早上 15 分钟，从头到尾**出声读一遍**。
> 读不顺、答不上来的，在标题前标 ⚠️，当天晚上重读。
> 连续 3 天能顺出来的，说明进了长期记忆，不用天天读了。
>
> **写新卡片的规则**：
> 1. 一张卡只问一个点
> 2. 问题要能 30 秒内答完
> 3. 答案必须包含「为什么」，不能只有「是什么」
> 4. 只记你已经**理解过**的东西，别抄别人的八股清单

## 卡片 001 · HashMap 默认容量

**Q**：HashMap 默认初始容量是多少？为什么必须是这个值？

**A**：16，且必须是 **2 的幂**。因为算下标用的是 `(n-1) & hash`，只有 n 是 2 的幂时，`(n-1) & hash` 才等价于 `hash % n`，而位运算比取模快得多。

**自测**：能说出「为什么必须是 2 的幂」，而不只是「是 16」。

---

## 卡片 002 · 负载因子 0.75

**Q**：负载因子为什么是 0.75，不是 1，也不是 0.5？

**A**：0.75 是**空间和时间的折中**。太低（0.5）浪费一半空间；太高（1.0）桶快满了，冲突激增，链表变长，查询退化。0.75 在泊松分布下，桶内元素达到 8 个的概率约为千万分之六，几乎不会树化。

---

## 卡片 003 · hash 扰动

**Q**：`hash(key) = h ^ (h >>> 16)` 这行在干什么？为什么要扰动？

**A**：把 hash 的**高 16 位**挪下来和低 16 位做异或。因为算下标只用了低位（`& (n-1)`），高位从来没参与过。扰动后高位信息混进低位，减少冲突。

**自测**：能说出「高 16 位」和「减少冲突」两个关键词。

---

## 卡片 004 · 取模转位运算

**Q**：`(n-1) & hash` 为什么能代替 `hash % n`？

**A**：当 n 是 2 的幂时，`n-1` 的二进制是「低位全 1」（如 16-1=15，即 1111）。与运算等于只保留 hash 的低位，效果和取模一样，但 CPU 执行速度快一个数量级。

---

## 卡片 005 · putVal 的分支

**Q**：`putVal` 有哪几个分支？按顺序说。

**A**：
1. 桶为空 → 直接 `new Node` 放进去
2. 桶首个节点 key 相同 → 覆盖
3. 是红黑树节点 → 走树插入
4. 是链表 → 遍历找相同 key，找到就覆盖；找到尾部就挂上去，挂完判断是否要树化
5. 插入完成 → `size++`，超过阈值就 `resize()`
6. 如果是覆盖 → **返回旧值**

---

## 卡片 006 · 覆盖

**Q**：`put` 一个已存在的 key，会发生什么？怎么拿到旧值？

**A**：旧值被覆盖（一个 key 只能有一个 value），但 **`put` 的返回值就是旧值**。不想覆盖用 `putIfAbsent`（对应源码里的 `onlyIfAbsent` 参数）。

---

## 卡片 007 · 数组 vs 链表

**Q**：数组和链表的区别？各自的复杂度？

**A**：
- 数组：内存**连续**，随机访问 O(1)，插入删除要搬元素 O(n)
- 链表：内存**分散**，靠 `next` 指针串起来，访问要遍历 O(n)，插入删除 O(1)
- 链表的节点装在堆上，每个节点多一个指针的空间开销

---

## 卡片 008 · 链表删除的坑

**Q**：遍历链表时，为什么不能写 `head = head.next`？

**A**：因为 `head` 是**唯一的入口**。改了它，前面的节点就再也找不到了，整条链会「断头」。正确做法是 `Node p = head;`，用 `p` 走，`head` 不动。

---

## 卡片 009 · fail-fast

**Q**：什么是 fail-fast？它靠什么实现？

**A**：集合在遍历过程中被结构性修改时（add/remove），会立刻抛 `ConcurrentModificationException`，而不是给出错误结果。实现靠 `modCount`：集合每次结构性修改 `modCount++`，迭代器创建时记下 `expectedModCount`，每次 `next()` 比较两者，不等就抛。

**注意**：它**不是并发安全的**，只是「尽早失败」。多线程下仍可能出错，那是 `ConcurrentHashMap` 的活。

---

## 卡片 010 · 树化的两个条件

**Q**：链表什么时候变成红黑树？为什么需要两个条件？

**A**：链表长度 ≥ **8**，**且** 数组容量 ≥ **64**（`MIN_TREEIFY_CAPACITY`）。如果容量不到 64，说明是「桶太多元素」不是因为冲突多，而是数组太小，此时优先 `resize()` 扩容，而不是树化。

---

## 卡片 011 · remove 的三种位置

**Q**：`remove` 一个 key 时，被删节点在桶内可能有哪几种位置？分别改哪个引用？

**A**：三种：

1. **桶是空的** → 不用删，直接返回 null
2. **节点是桶首** → 改 `table[i] = node.next`
3. **节点在链表中间或尾部** → 改 `prev.next = node.next`（尾部时 `node.next` 恰好是 null，不用特判）

**自测**：能说出「头节点改的是 `table[i]`，不是某个节点的 next」。

---

## 卡片 012 · 为什么必须有前驱 prev

**Q**：单链表删除节点，为什么手里必须有前驱 `prev`？为什么把它初始化为 `null`？

**A**：单链表不可逆向，拿不到前驱就改不了指向它的那条 `next`。所以遍历时一边走一边把前一个节点存进 `prev`。

`prev` 初值给 `null` 是当**哨兵**：`null` 表示「当前节点没有前驱」，也就是它是桶首。

这样一个 `if (prev == null)` 就把「改 `table[i]`」和「改 `prev.next`」分开了，不需要为头节点单独写一套循环。

## 卡片 013 · 删除后为什么不缩容

**Q**：HashMap 删除元素后为什么不缩容？

**A**：三条理由：

1. 扩容的触发条件是 `size > threshold`。一缩容 `threshold` 就跟着降，同一批元素立刻又超阈值 → **反复扩容/缩容抖动**
2. 缩容要 **rehash 全部元素**，代价大，而收益只是省一点内存
3. 设计上**容量只增不减**（上限 `1 << 30`），从根上排除抖动

**自测**：能说出「阈值会跟着降，导致抖动」这一条，而不只是「不缩容」。

## 卡片 014 · removeNode 的树分支

**Q**：JDK 8 的 `removeNode` 遇到红黑树桶怎么处理？什么时候退化成链表？

**A**：桶首是 `TreeNode` 时走 `removeTreeNode`。删完之后如果树已经很小（root 为 null，或左右子树缺得太厉害），就 **untreeify** 把树拆回链表。

注意和树化条件对称着记：树化要 **链表 ≥ 8 且容量 ≥ 64**；退化看的是**树的形态太小**。

---

## 卡片 015 · remove 不存在的 key

**Q**：`remove` 一个不存在的 key，`size` 要不要变？返回值是什么？

**A**：`size` **不变**。契约是：删到了才 `size--` 并返回旧 value；没删到返回 `null`，什么也不动。

所以别用返回值判断「删没删到」—— 被删的 value 本身可能就是 `null`。要判断就用 `remove(key, value)` 的布尔重载。

---

## 卡片 016 · 摘下来要不要置 null

**Q**：节点从链表上摘下来之后，要不要手动把它的 `next` 置 null？

**A**：**不需要**。摘下来之后没人引用它，GC 会回收。

更要小心的是反着写错：`prev.next = null` 会把被删节点后面的**整条链丢掉**（`prev.next` 就是下一个节点）。

真正需要手动置 null 的是另一种场景：对象**仍被引用**、但内部引用不再需要（如 `ArrayList.clear()` 把每个槽位置 null），那是防内存泄漏。

---

## 卡片 017 · 手写删除最易错的两处

**Q**：手写链表删除时最容易犯的两个错？

**A**：

1. **循环条件漏取反**：`while (cur != null && !keyEquals(key, cur.key))`。少个 `!` 就一次都不进循环，直接掉进「删头节点」分支，**无条件删掉桶首**
2. **把 `prev` 当成当前节点**：`prev` 一旦和 `cur` 指同一个节点，循环跑起来后语义就乱了

**自测**：能说出「少一个 `!` 会导致无条件删头节点」才算真的踩过这个坑。

---

## 卡片 018 · 面试追问：能不能只把 value 置 null

**Q**：面试官问「remove 时偷懒只把 value 置 null 行不行？」怎么答？

**A**：不行，四个理由：

1. key 还在链表里，**`size` 不变**，遍历和统计全错
2. `Node.key` 是 `final`，这个位置**复用不了**，新 put 同一个 key 还得再挂一个节点
3. 扩容时这个「已删」节点**还会被搬到新表**，白占内存
4. `get` 返回 null 但 `containsKey` 返回 true，**语义自相矛盾**
